# Устройство

English: [docs/en/architecture.md](en/architecture.md)

Как устроен FlyArchive: из каких служб он состоит, где лежит код и где данные, как документ попадает в архив, как он ищется и как его открывает человек. Всё
здесь сверено с кодом; значения по умолчанию взяты из схемы настроек (`tools/settings.py`, справочник печатает `python3 tools/settings.py --reference`), а не
из чьей-то установки. Как поставить и эксплуатировать — в `docs/operations.md`, требования по карточкам — в `docs/requirements.md`.

## Общая схема

```
  машина архива                                другие машины частной сети
  ─────────────                                ──────────────────────────
  браузер ── DSH :3080 ─┐                      оболочка модели + токен
  оболочка в песочнице ─┤                               │
                        ▼                               ▼
                   MCP :8767  ◄──────────  шлюз  <адрес частной сети>:8780
                    │      │               (/mcp по токену, /doc и /file
                    ▼      ▼                по подписанной ссылке)
           поиск :8765   документы :8766
           LanceDB       Docling, matplotlib, graphviz,
           + служба      приём документа во входящую папку
           векторов
                │              │
            индекс         корпус ◄── входящая папка ── приёмка ── таймер
```

DSH, шлюз и песочница необязательны: ядро — входящая папка, приёмка, индекс и поиск — работает командами и без служб (см. «Установка»).

Плагин DSH — путь владельца, а не модели: в MCP он не ходит, а зовёт команду `flyarchive`. Он состоит из двух половин: серверная живёт в процессе DSH и
запускает команду, браузерная рисует раздел настроек и вкладку.

```
  браузер: вкладка Archive, Settings → Archive
        │  fetch /api/flyarchive.*   (вход самого DSH: cookie сеанса, проверка Host и Origin)
        ▼
  DSH :3080 ── плагин, серверная половина (dsh-plugin/lib/index.js)
        │  проверка запроса, затем execFile без оболочки: аргументы списком, пути после «--»
        ▼
  flyarchive … --json   (tools/flyarchive)
        │
        ├─ входящая папка, пачки, ход разбора, решения   inbox.py, batches.py, progress.py, review.py
        ├─ просмотр файлов                               preview.py, preview_worker.py, preview_container.py
        ├─ описание изображений                          vision.py
        └─ токены, журнал, удаление документа            tokens.py, journal.py, review.py
```

Службы архива слушают только петлю: адрес прослушивания в них не настраивается. Единственная дверь наружу — шлюз на адресе машины в частной сети. Под WSL
петля видна и программам Windows: службы архива закрыты токеном, а служба векторов и сервер локальной модели не принадлежат архиву — их адреса задают
настройки `embed_url` и `llm_local_url`, и закрывать их от чужих обращений должен тот, кто их поставил.

## Службы и порты

| Адрес по умолчанию | Что | Файл |
|---|---|---|
| `127.0.0.1:8765` (`search_port`) | поиск: страница, `/api/search`, `/doc`, `/openapi.json` | `tools/webui.py` |
| `127.0.0.1:8766` (`office_port`) | документы и графика, приём документа по MCP, `/openapi.json` | `tools/office_server.py` |
| `127.0.0.1:8767` (`mcp_port`) | переходник MCP над первыми двумя | `tools/mcp_server.py` |
| `<gateway_bind>:8780` (`gateway_port`) | шлюз в частную сеть: MCP и подписанные ссылки; без `gateway_bind` не запускается | `tools/gateway.py` |
| `127.0.0.1:3080` (`dsh_port`) | DeepSeek Harness с плагином: раздел Archive в настройках и вкладка Archive в правой панели | `tools/dsh-web-start`, `dsh-plugin/` |
| — | разбор входящей папки по таймеру (по умолчанию каждые 30 минут); в конце прохода описание изображений | `tools/inbox.py`, `flyarchive-inbox.timer` |
| `127.0.0.1:11434` (`embed_url`) | служба векторов с интерфейсом `/api/embed` (ollama): векторы `bge-m3`; не часть архива | ставит владелец |
| `127.0.0.1:8080` (`llm_local_url`) | сервер локальной модели с интерфейсом OpenAI: проверка при приёмке и описание изображений; не часть архива | ставит владелец |

Серверы поиска и документов разделены намеренно: разбор стостраничного pdf занимает секунды и в общем процессе задерживал бы выдачу поиска. Переходник MCP
переспрашивает у этих двух серверов, а не повторяет их. Службу векторов можно заменить любой, что отвечает так же; модель векторов и её размерность — настройки
`embed_model` и `embed_dim`.

Один адрес служб поиска и документов в таблице назван без пояснений. `/openapi.json` есть у обеих служб: это описание их инструментов в формате OpenAPI для оболочки,
которая берёт инструменты по OpenAPI, а не по MCP; оно отдаётся только с токеном (уровня «чтение» и выше) и только на петле. Шлюз пропускает наружу только `/mcp`, `/doc` и `/file`,
поэтому с других машин `/openapi.json` недоступен.

### Плагин DSH

Плагин `flyarchive-dsh-plugin` — две половины, которые говорят друг с другом только по адресам `/api/flyarchive.*`. Сам он ничего не делает: хранилище токенов,
журнал и приёмку не читает и их формата не знает, всё идёт через команду `flyarchive`.

- **Серверная половина** (`dsh-plugin/lib/index.js`) регистрирует адреса в соединении DSH. Пускает на них сам DSH: проверка `Host` и `Origin` и подписанная cookie
  сеанса, поэтому работать с архивом может только человек, вошедший в DSH на машине архива. Каждый запрос плагин проверяет до вызова команды: имена и уровни,
  границы чисел, форму пути (непустой, без управляющих знаков, не похож на ключ), список из не больше чем 200 путей без повторов, вид номера пачки, область
  просмотра, глубину вложений, номер страницы. Дальше он запускает `flyarchive … --json` через `execFile`: оболочки нет, аргументы идут списком, пути — после `--`, и
  файл с именем `--yes` ключом не станет. Отказ команды (последняя строка stderr — JSON `{"error": …}`) приходит клиенту как 409 с сообщением; код 2 команды (разбор
  аргументов) и всё прочее — 502 с общим текстом, сырой stderr наружу не уходит, а похожее на токен стирается. Значение токена попадает в ответ только при выпуске.
  Срок ожидания команды: 20 секунд на обычный вызов, 15 минут на принятие и удаление (индексация идёт на процессоре), 300 секунд на просмотр. Путь к команде плагин
  берёт из своей настройки (`command` в файле настройки оболочки: установка пишет в него запускалку команды `<каталог архива>/bin/flyarchive`), иначе из переменной окружения `FLYARCHIVE_CLI`, иначе берёт
  имя `flyarchive` из пути поиска команд (запуск по-прежнему без оболочки); не нашлась — отказ с подсказкой, какой настройкой задать путь.
- **Браузерная половина** (`dsh-plugin/lib/client.js` и словарь сообщений `client.messages.js`) написана без сборщика, в формате загрузчика модулей DSH. Она ставит
  раздел в настройки и тип вкладки в правую панель (вкладка одиночная и остаётся смонтированной), заголовок вкладки и запись в путеводителе панели. Словарь
  сообщений загружается отдельным запросом (`require.async`): хост DSH отдаёт только `client.js` и соседей вида `client.<имя>.js`.

Общее хранилище состояния и один опрос. Вкладки правой панели живут внутри сеанса разговора, а сеансов может быть много; опрашивать сервер каждому было бы
расточительно. Поэтому состояние — одно общее хранилище на раздел настроек, тело вкладки, её заголовок и всплывающее сообщение, а опрашивает сервер только
корневой эффект плагина: раз в 30 секунд, пока страница видна, раз в 2 секунды, пока идёт разбор, скрытая страница не опрашивает вовсе. Списки очереди и
карантина перечитываются, только когда изменились счётчики или номер последней пачки. Заголовок «Archive (N)» и сообщение об окончании пачки (`Toast` из
примитивов DSH в собственном корне React плагина) читают то же хранилище. Службы вкладки, языка и `Toast` — внутренние для DSH и могут измениться с его
обновлением: если их нет, плагин не падает, раздел настроек работает как раньше, а сообщение просто не показывается.

## Код и данные

Код и данные разделены. **Код** — каталог `tools` репозитория (и `dsh-plugin` для плагина); службы запускаются из того каталога, откуда шла установка. **Данные,
журналы и секреты** — каталог архива: `~/flyarchive` или `FLYARCHIVE_HOME` (настройка `home`, единственная, которой нет в `settings.json`, потому что файл лежит в
самом каталоге). Кода в каталоге архива нет: там лежит только запускалка команды `bin/flyarchive`, короткий файл sh, который пишет установка. Каждая служба получает каталог архива одной переменной окружения; адресов, портов и имён узла в файлах служб нет:
они читают настройки при запуске.

Настройки складываются из трёх слоёв: умолчание в коде (не привязано к машине), файл `settings.json` в каталоге архива, переменная окружения
`FLYARCHIVE_<КЛЮЧ ЗАГЛАВНЫМИ>`; у каждой настройки одна переменная, сильнее — последний слой. Значения ключей моделей в настройки не попадают вовсе: ключ локальной модели берут
из переменной `FLYARCHIVE_LLM_KEY` или из файла, путь к которому задаёт `llm_key_file`, ключ запасной облачной модели — из переменной `FLYARCHIVE_LLM_CLOUD_KEY` или из файла,
путь к которому задаёт `llm_cloud_key_file`. Настройки приёмки (входящая папка, период разбора, проверка моделью,
запасная облачная модель, порог, пределы распаковки, описание изображений) в общую схему не входят: они лежат в `inbox.json` каталога архива, их меняют
`flyarchive inbox set` и раздел Intake в DSH, и одна настройка живёт в одном месте — сохранённое из DSH значение не перебьют ни окружение, ни `settings.json`.
Таблица источников (`sources.json`, необязательная) лежит там же: она называет корни корпуса и базы индекса. Образцы обоих файлов — `settings.example.json` и
`sources.example.json`.

Файл настроек и таблица источников читаются только если принадлежат владельцу и не открыты для записи другим; хранилище токенов и каталог `secrets` закрыты правами
700 и 600. Секретов в настройках нет, а значения настроек не попадают в сообщения об ошибках.

## Установка

`flyarchive install` (`tools/install.py`) пишет всё из шаблонов `tools/templates` по настройкам и не держит ничего «в голове»: ни адресов, ни имён узла, ни путей
чужой машины в шаблонах нет, а подстановка с неизвестным именем — ошибка, а не пустое место. По шагам:

1. **Архив.** Тот же код, что у `flyarchive init`: каталоги с правами владельца, служебный токен, пустая база известного, пустая таблица индекса с полнотекстовым
   индексом. Готовое не пересоздаётся.
2. **Службы и таймер.** `flyarchive-search`, `flyarchive-office`, `flyarchive-mcp` (один шаблон на Python-сервис), `flyarchive-gateway` (только если заданы
   `gateway_bind` и `public_url`), `flyarchive-dsh` (только если `dsh` есть в пути поиска и не указано `--no-dsh`) и пара `flyarchive-inbox.service` с
   `flyarchive-inbox.timer`. Тот же код и те же шаблоны переписывают службу и таймер разбора при `flyarchive inbox set` (с ключом `--no-timer` команда только
   сохраняет настройки). Путь к коду, интерпретатор и каталог архива попадают в файл службы, поэтому путь с пробелом или знаком `%` `"` `'` `\` `$` останавливает
   установку до записи.
3. **Плагин.** Папка `dsh-plugin` (`package.json` и `lib`) кладётся в `<dsh_profile>/node_modules/flyarchive-dsh-plugin`; прежняя папка заменяется целиком, соседние
   каталоги профиля не трогаются. Нет профиля — шаг пропускается.
4. **Файл настройки оболочки** `<каталог архива>/dsh.patch.yml` из `tools/templates/dsh.patch.yml`: подключение сервера MCP архива и плагина. Служебный токен и ключи
   в него не пишутся: запускалка оболочки читает их при старте.
5. **Команда в пути поиска.** Запускалка команды `<каталог архива>/bin/flyarchive` (sh, права 0700: `exec` файла команды интерпретатором, которым шла установка) и ссылка
   `<bin_dir>/flyarchive` на неё; чужой файл с тем же именем не трогается. Запускалкой команду зовут и плагин (строка `command` файла
   `dsh.patch.yml`), и `tools/dsh-web-start`: у файла команды первая строка `#!/usr/bin/env python3`, а библиотеки стоят в Python установки.
6. **Запуск.** `systemctl --user daemon-reload`, `enable --now` для служб по порядку зависимостей, `enable --now` и `restart` для таймера.

Шлюз ставится, только когда заданы оба ключа, `gateway_bind` и `public_url`; заданные значения установка не перезаписывает. С `--gateway auto` адрес и имя узла берутся
у tailscale (`tailscale ip -4`, `tailscale status --json`), адрес обязан быть из диапазона частной сети (100.64/10), и в `settings.json` дописываются только
недостающие ключи. `--dry-run` ничего не трогает и печатает каждый файл (запускалку тоже) и каждую команду systemctl. Нет `systemctl` или каталога профиля — шаг пропускается, а не
падает. Повтор установки безопасен.

## Доступ

Каждый запрос несёт токен. Хранятся только хеши токенов; уровни — `read`, `full`, `local`.

| Кто | Как входит | Что может |
|---|---|---|
| DSH на машине архива | служебный токен уровня `local` из закрытого файла | всё, что есть в MCP |
| оболочка внешней модели на машине архива | свой токен; запуск в песочнице `flyarchive run` | по уровню токена; файлов архива не видит |
| другая машина частной сети | свой токен, только через шлюз и только MCP | по уровню токена |
| браузер по ссылке из ответа | подпись в ссылке, срок `link_ttl_s` (по умолчанию сутки) | открыть один документ |
| владелец | команда `flyarchive`, раздел Archive в настройках DSH и вкладка Archive | токены, очередь, карантин, удаление, параметры, просмотр файлов |

Удаление, решения по очереди и карантину, выпуск токенов по MCP не выставлены вовсе. Каждое обращение пишется в журнал `logs/access.jsonl` под именем клиента;
значений токенов в нём нет.

Журнал называет и отозванный токен. Проверка токена (`tools/tokens.py`) умеет ответить не только «подходит ли», но и «чей это негодный токен и почему»: хеш
сравнивается по всем строкам хранилища за одинаковое время, а на пути отказа ничего не пишется, в том числе «последнее обращение». Общий код входа
(`tools/auth.py`, один на поиск, документы и MCP) отвечает клиенту прежним 401 и общим текстом «токен неверен, отозван или просрочен» — состояние токена наружу не
раскрывается, — а в журнал пишет имя и уровень токена и исход «отказ: токен отозван <время>» или «токен просрочен <время>»; при обоих признаках пишется
«отозван». Значение без строки в хранилище пишется как клиент «-». Удачный список инструментов в журнал не идёт намеренно: клиент-ассистент переподключается
каждые полчаса, и это был бы шум; вызовы инструментов пишет та служба, которая их выполняет, под именем клиента, а переходник MCP — только подключение.

Инструменты MCP помечены по спецификации (`annotations` в `tools/mcp_server.py`): три читающих — «только чтение», пять создающих — «не разрушает», все —
«замкнутый мир». Клиенты, которые спрашивают человека про инструменты без пометок, читающие пропускают сами. Служебные поля `route` и `need` наружу не уходят.
Что пометка совпадает с уровнем токена, держит `tests/test_mcp_annotations.py`.

Песочница (`tools/sandbox.py`, bwrap): система только для чтения, рабочий каталог на запись, отдельный домашний каталог, сеть общая. Архива, домашнего каталога
владельца, дисков Windows, сокета docker и чужих процессов внутри нет. Песочница защищает файлы, а не сеть; сеть закрывают токены.

## Пополнение: входящая папка

```
входящая папка ──► ждёт 30 с без изменений
        │
        ▼
   приёмка (tools/gate.py, intake.py)
     тип по содержимому · распаковка архивов с пределами · правила и баллы
     сверка с архивом: письмо по Message-ID, файл по sha256
     проверка моделью, если она включена: локальная, а если молчит llm_timeout_s — запасная, если она настроена
        │
        ├─ принят ────────► corpus/входящие/<пачка>/ ──► индекс, база «входящие»
        ├─ находки ───────► очередь/<пачка>/        ждёт решения владельца
        ├─ программа ─────► карантин/<пачка>/
        ├─ не содержимое ─► убирается: пустой файл, след системы (в квитанции «пропущен»)
        └─ не взят ───────► <входящая>-возврат/<пачка>/
        ▼
   сверка sha256 копии с исходником ──► исходник убран ──► квитанции/<пачка>.jsonl + <пачка>.meta.json
        ▼
   долги индексации (ещё раз) ──► описание картинок и сканов, этап vision ──► индекс
```

Пока идёт проход, этап и счёт пишутся в `inbox-progress.json`: его читает вкладка.

Входящая папка по умолчанию — `<каталог архива>/входящие`; папка возврата лежит рядом и называется так же с суффиксом `-возврат`. Настроенная папка обязана лежать вне
архива и не содержать его.

**Что убирается и что возвращается.** Исходник убирается из входящей папки, только когда его точная копия сохранена (в корпусе, очереди или карантине, либо он уже был в архиве
точным повтором) или когда он не содержимое: пустой файл и служебный след операционной системы (каталог `__MACOSX` и всё в нём, `.DS_Store`, `Thumbs.db`, `desktop.ini`, `._<имя>` с подписью
AppleDouble или внутри `__MACOSX`). Перечень следов задан в коде (`intake.py`, функция `trace_reason`), не меняется ничем снаружи и смотрит на имя файла (у `._<имя>` ещё и на подпись в его начале); программа под таким именем
всё равно идёт в карантин. Такой файл получает решение «пропущен» с причиной в квитанции (в отчёте приёмки у него метка `skipped_as` со значением `trace`), не мешает убрать папку или архив,
где лежал, и в папку возврата не идёт. Всё прочее, что архив не взял, возвращается, а архив с таким членом — целиком. Служебные файлы по шаблонам имён (`service_names` — в любой папке,
`service_root_names` — в корне входящей папки или архива; по умолчанию пусты, поэтому текстовый файл с любым именем — документ) и описание письма (`.json` рядом с одноимённым письмом)
приёмка помечает `skipped_as` со значением `service`, а судьбу помеченного решает параметр `service_fate` из `inbox.json`: `return` (по умолчанию) — возврат, `delete` — файл убирается,
как след. Решает это разбор входящих (`inbox.py`): сама приёмка источник не изменяет.

Модель при приёмке только добавляет находки: снять баллы правил она не может, в карантин сама не отправляет. Документ для неё — данные между случайными метками.
Картинки и сканы проверяет только локальная модель. Модели нет или она недоступна — проверка не даёт вердикта, и документ получает находку «модель не проверила: …»
уровня HIGH: он ждёт решения владельца при любом пороге (владелец, у которого модели нет, выключает проверку: `flyarchive inbox set --llm off`).

Очередь, карантин, квитанции и `удалённое/` лежат в каталоге архива, но вне корпуса: в индекс они не попадают.

**Пачка и её история.** Проход, в котором были файлы, получает номер `ГГГГММДД-ЧЧММСС`; вторая пачка в ту же секунду — с `-2` и так далее. Квитанции
`квитанции/<пачка>.jsonl` — запись на каждый файл приёмки, после них дописываются строки решений владельца (поле `by`: принять, в карантин, вернуть, стереть). Рядом
`<пачка>.meta.json` (права 0600): время начала и конца, секунды и замечания прохода сообщениями с кодами. Прежние читатели квитанций отбирают только `.jsonl` и файла
замечаний не видят. История (`tools/batches.py`) собирается из этих файлов: список пачек от новой к старой со счётом по решениям приёмки (строки владельца в счёт не
идут) и подробности пачки — запись на файл плюс последнее решение владельца и `location`, где файл лежит сейчас. Три места (`corpus`, `queue`, `quarantine`)
проверяются наличием файла. `returned` и `deleted` следуют из записей: файл вернули приёмка или владелец; владелец стёр его из карантина или убрал документ из
архива, и тот найден в `удалённое/`. `missing` — по квитанции файл должен лежать в одном из трёх мест, а его там нет; `null` — хранить было нечего. Номер пачки
проверяется по виду, прежде чем из него сложится имя файла; строка квитанции, которая не разбирается, пропускается. Квитанция пишется один раз, до описания
изображений, и после не меняется: дописывает к ней только владелец. Живое состояние описания берётся при показе пачки по sha256 из файла описания и долгов.

**Ход разбора.** Пока проход держит замок `inbox.lock` (одновременно идёт один), он пишет `inbox-progress.json`: этап, сколько готово из скольких, последний готовый
файл, номер пачки, `pid`. Запись идёт через временный файл и `os.replace`, права 0600, не чаще четырёх раз в секунду; смена этапа и последняя запись этапа пишутся
всегда, а пока один документ индексируется или описывается, отдельный поток переписывает запись, если её не трогали 20 секунд, чтобы живой проход не выглядел
брошенным. Этапы: `intake` (распаковка и правила), `model` (проверка моделью), `settle` (раскладка и сверка копий), `index` (индексация), `sources` (уборка
исходников), `vision` (описание изображений); всего файлов на `intake` может быть неизвестно. Состояние (`flyarchive inbox status`) отдаёт запись как `progress`
или `null`, если файла нет, процесса с таким `pid` нет или запись старше десяти минут. Файл, оставшийся от убитого прохода, ничей: следующий проход под замком его
убирает. Сбой записи хода разбор не останавливает.

**Долги.** Два файла долгов под одним замком `index/pending.lock`: `index/pending.jsonl` — документ лежит в корпусе, а в индексе его нет (индексация не удалась или
принятие шло без ожидания), и `index/vision-pending.jsonl` — картинка или скан без текста ждёт описания. Чтение, правка и запись (через временный файл) — одно
действие под замком, поэтому принятие владельцем и проход идут одновременно, и долги не теряются и не задваиваются. Проход отдаёт долги индексации в начале и ещё
раз в конце: долг, записанный, пока он шёл, индексируется им же. Долги описания отдаются раз в конце прохода и командой `flyarchive vision run`; сам шаг держит свой
замок `index/vision.lock`, чтобы проход и команда не сталкивались, а занятый шаг не ждёт, а пропускается.

**Решения пачкой и принятие без ожидания.** `queue accept`, `queue quarantine` и `quarantine return` принимают до 200 путей и отвечают записью на путь; негодный
путь остальных не останавливает (`review.decide_many`). `queue accept --defer-index` переносит файл в корпус и базу известного, пишет долг индексации и запускает
службу разбора (`systemctl --user start --no-block`), но индексации не ждёт: вкладка принимает именно так. Сменить входящую папку можно командой
`inbox set --path … --must-exist`: каталог должен существовать, лежать вне архива и не содержать его; смена пишется в журнал обращений.

### Как наполняется архив

Открытый путь пополнения один: входящая папка. Положенный в неё файл, папка или архив проходит приёмку и, если принят, попадает в корпус и в индекс; тот же путь у
документа, переданного по MCP (`submit_document`). Массовой первичной загрузки в открытой части нет: выгрузки почты, страниц и файловых папок и их разбор — работа владельца
вне неё. Если такие выгрузки уже лежат в `corpus`, их индексирует дозаполнитель `tools/index_more.py`: он обходит корни, названные в таблице источников
(`sources.json`), и каталог `входящие`, режет текст на фрагменты по 4000 знаков (с перекрытием 200, из файла берутся первые 400 000 знаков), считает векторы и пишет
их в таблицу. Он возобновляемый — пройденные файлы записаны в `index/ingested.txt` — и не заходит в каталоги `_карантин`. Принятое
через входящую папку полный обход включает, так что пересборка индекса его не теряет.

Извлечение текста: `PyMuPDF` для pdf, `python-docx`, `openpyxl`, `python-pptx`, `extract-msg` для писем .msg, стандартная библиотека для .eml, разбор разметки для
`bpmn`, `svg`, `drawio`, `xml`, `html`, простые текстовые форматы читаются как есть. Картинки и сканы без текстового слоя текста для индексатора не дают: их описывает
локальная модель (см. «Описание изображений»). Путь из индекса в файл корпуса разбирает один модуль, `corpus_path.py`: им пользуются и сервер поиска, и сервер
документов.

## Просмотр

Вкладка Archive показывает содержимое файла из очереди, карантина или корпуса, а файл при этом непроверенный и может быть вредоносным. Правило одно: байты такого
файла читает только процесс в песочнице без сети или контейнер без сети, а в браузер уходит только PNG и простой текст.

```
  вкладка ── POST (тело: область, путь, вложения, страница) ──► плагин: проверка запроса, execFile, срок 300 с
                                                                  │
                                                                  ▼
                                      flyarchive preview show | page      родитель (tools/preview.py)
                                      ссылка по именам · sha256 потоком · кэш · замки
                              ┌───────────────────────┴───────────────────────┐
                              ▼                                               ▼
                 рабочий процесс в bwrap, без сети            контейнер docker, без сети (Office, HTML, метафайлы)
                 PDF, картинки, текст, письма, архивы         soffice → PDF; дальше его рисует рабочий процесс
                              └───────────────────────┬───────────────────────┘
                                                      ▼
                         проверка ответа как данных (обычный файл, размер, PNG, схема) → кэш по sha256
                                                      ▼
                         в браузер: PNG (image/png, nosniff, sandbox) и простой текст
```

Ссылка на файл — область (`queue`, `quarantine`, `corpus`), путь и до двух номеров вложений. Родитель (`preview.py`) проверяет её по именам: путь без `..`, не
абсолютный, без ссылок, внутри названной области (тот же разбор, что у решений владельца и у `corpus_path`). Только после этого файл открывается, и родитель читает его
потоком, чтобы посчитать sha256. Тип и содержимое определяет рабочий процесс (`preview_worker.py`): он идёт в `bwrap` с `--unshare-all` без сети, видит свой входной
файл, каталог кода и библиотеки Python (всё только для чтения) и пустой выходной каталог; интерпретатор — настоящий, которым запущен родитель (у виртуального окружения это его базовый
интерпретатор): лежит он вне системных каталогов — каталог его установки привязан только для чтения, а если так отдать его нельзя безопасно, просмотр отвечает отказом
`preview.python_outside`. Песочницу может запрещать сама система, поэтому `flyarchive doctor` пробует найденный `bwrap` коротким запуском (`bwrap --unshare-all --ro-bind / / true`)
и называет причину отказа; пределы памяти, времени процессора и размера записи ставятся внутри
процесса до импорта библиотек. Рабочий процесс описывает файл (вид, страницы, текст, письмо со списком вложений, состав архива) и рисует страницу в PNG; вложение
письма он только достаёт в выходной каталог, а открывается оно новым рабочим процессом под своим sha256.

Контейнер нужен для Office, HTML и метафайлов. Родитель кладёт в свой каталог копию байтов из уже открытого файла (её sha256 сверяется) и запускает `docker run` по
закреплённому образу с фиксированным набором ключей: `--network none`, `--read-only`, `--cap-drop ALL`, `no-new-privileges`, 256 процессов, 2 ГБ памяти, 2 ядра, вход
только для чтения, отдельный выходной каталог, `--pull never` (нет образа — отказ, а не скачивание). Образ записывается командой `flyarchive preview setup` вместе с
дайджестом (`preview.json` в каталоге архива): контейнер запускается только по дайджесту. Срок преобразования стоит внутри контейнера (`timeout -s KILL 120`), поэтому он
завершится, даже если родителя убили; родитель к тому же по истечении срока останавливает и удаляет контейнер по имени `flyarchive-preview-<uuid>`, а каждая команда
`preview` при старте отдельным процессом убирает такие контейнеры старше пяти минут. Из выходного каталога родитель принимает ровно один обычный файл, начинающийся с
`%PDF-`, и кладёт его в кэш как `base.pdf`. Дальше это обычный PDF, и рисует его тот же рабочий процесс в `bwrap`.

Что вернул рабочий процесс или контейнер, проверяется как данные до записи в кэш: обычный файл (не ссылка), размер, начало и конец PNG, описание по схеме с
пределами. Не прошло — ответ `kind: "none"` с сообщением, исключение наружу не выходит, чужое в кэш не попадает. Результат `none` в кэш не пишется.

**Кэш и замки.** Кэш — `cache/preview/<sha256>/` (каталоги 0700, файлы 0600, запись через временный файл и `os.replace`): `desc.json`, `page-N.png`, у Office ещё
`base.pdf`. Ключ — sha256 тех байтов, что рисуются: у вложения письма свой, а одно и то же вложение из разных писем рисуется один раз. Замки (`flock`): на описание
объекта, на каждую страницу, два слота на рабочие процессы (третий ждёт) и общий замок рендера `.render.lock`: одновременно идёт одно преобразование в контейнере.
Запрос, заставший замок занятым, не ждёт, а получает `kind: "rendering"`, и вкладка переспрашивает раз в 2 секунды до трёх минут. `preview page` преобразование не
запускает никогда: нет готового `base.pdf` — отказ; два запроса одной страницы рисуют её один раз. Кэш чистится по возрасту (7 дней) и объёму (2 ГБ) командой
`flyarchive preview clean` и сам, когда объём превышен.

**Что уходит в браузер.** Серверная половина плагина возвращает описание как есть, а страницу — байтами PNG с `Content-Type: image/png`,
`X-Content-Type-Options: nosniff` и `Content-Security-Policy: sandbox`; ответ, который не начинается с подписи PNG, отдаётся отказом 502. Запрос страницы идёт телом,
путь файла в адрес не попадает. Текст письма, имена вложений, строки архива и текст документа браузерная половина выводит только как текст: никакой разметки из
содержимого на страницу не попадает. Типы просмотра: текст, PDF, SVG, картинки, письма с вложениями, состав архивов, календарь и Office, HTML, метафайлы через
контейнер. BPMN, draw.io, видео и звук не сделаны: для них ответ — `kind: "none"` с пояснением «нужен преобразователь».

## Описание изображений

Картинки и сканы без текстового слоя принимаются, но в индекс сами не попадают: у индексатора нет текста. Их описывает локальная модель со зрением, и описание
ложится в индекс.

```
проход:  приёмка ─► раскладка ─► квитанции ─► долги индексации ─► шаг описания (этап vision) ─► запись хода и замечаний пачки
              │
              └ картинка или скан без текста: долг «ждёт описания» → index/vision-pending.jsonl

шаг:     долг ─► просмотр даёт PNG страницы (до 4 Мп) ─► локальная модель, страница за запросом
              ─► правила приёмки на тексте описания ─► index/vision/<sha256>.json ─► фрагменты в индексе под путём исходного документа
```

Место шага в проходе — в конце, после квитанций и после повторной отдачи долгов индексации; поэтому квитанция называет только причину ожидания, а живое состояние
(описан, ждёт, сколько страниц, какая модель, сколько секунд) отдаёт `inbox.vision_state` по sha256. Проход без новых файлов, но с долгами описания идёт без пачки и
начинается сразу с этапа `vision`. В долги описания попадает всё, что индексирует: проход, отдача долгов индексации и принятие из очереди.

Картинку для модели готовит просмотр (`preview.page`), так что непроверенный файл по-прежнему читает только рабочий процесс в песочнице. Сам шаг (`tools/vision.py`)
файл не открывает и не разбирает: число страниц он берёт у `preview.show`, размер картинки — из заголовка PNG, который вернул просмотр. Описываются первые 20 страниц
документа; страница меньше 120 точек по стороне не описывается.

Только локальная модель. Запрос уходит локальной точке из `llm_check` (адрес, ключ и имя — из настроек `llm_local_url`, `llm_key_file` и `llm_local_model`), облачный
запасной путь у этого шага не собирается вовсе, даже если он настроен. Запрос без инструментов, температура 0, размышление выключено, ответ до 1 500 токенов, срок
`llm_timeout_s` (по умолчанию 180 секунд); запросы идут по одному, а перед каждым проверяется, что модель готова: сервер, который сообщает перечень загруженных
моделей (`swap_running`), должен назвать в нём нужную, а сервер без перечня считается готовым. Запрос и описание — по-русски. Сервер, отвергший дополнительные поля
запроса кодом 400, получает тот же запрос ещё раз без них.

Описание — данные. Управляющие знаки убираются, длина ограничена, ключ модели затирается, текст проходит `gate.scan_text`. Страница с находкой HIGH или CRITICAL в индекс
и в файл описания не идёт, остаются номер страницы и название правила. Указание, которое написано на картинке, попадает в описание как надпись и ничего не меняет.

**Файл описания** — `index/vision/<sha256>.json` (0600, каталог 0700, запись через временный файл и `os.replace`). Имя только sha256: ни имени документа, ни текста в
пути нет. Файл пополняется по странице: сбой одной страницы или остановка модели сделанного не теряют, а описание того же содержимого повторно не делается. Он
отдельный от индекса намеренно: индекс можно пересобрать без модели. В индекс описание ложится фрагментами того же документа (тот же `path`, источник и дата), а
описание каждой страницы начинается с пометки «Описание изображения, сделанное моделью (страница N):». Поиск находит такой фрагмент как любой другой и ведёт на
исходный документ.

**Долги под замком.** Долги лежат в `index/vision-pending.jsonl` под тем же замком `index/pending.lock`, что и долги индексации, но отдельным файлом: у долга описания
свой бюджет, своя причина ожидания и свой счётчик неудач. Один шаг описания за раз держит `index/vision.lock`; занятый шаг пропускается, а не ждёт. За проход шаг
описывает не больше заданного числа страниц и не дольше заданных минут (по умолчанию 60 и 10), остальное остаётся долгом. Два вида сбоя: модель не ответила, не
загружена, занята или вышел срок — остановка всего шага, долги целы, в замечаниях пачки одна запись; страница не далась (негодный ответ, отказ просмотра) — сбой
страницы, остальные страницы и документы идут. Ответ просмотра «ещё рисуется» — ожидание, а не неудача: счётчик попыток растёт только от настоящих отказов, страница, не
давшаяся три прохода, пропускается. Описание, которое не удалось проиндексировать, остаётся в файле: повтор идёт без модели.

Старые документы архива без текста в индексе описываются только по команде: `flyarchive vision backfill --limit N` записывает их долгами (модель не зовёт), а
`flyarchive vision run` или проход их описывает. `flyarchive doc delete` убирает файл описания и долги документа, если то же содержимое не лежит в архиве под другим
путём.

## Сообщения с кодами

Всё, что система говорит человеку, имеет код и параметры; русский текст остаётся прежним. Экран плагина английский, терминал русский, и мост между ними — код.

**Каталог** — `tools/messages.py`: код → русский шаблон и имена параметров (больше двухсот кодов). Коды вида `область.что_случилось` (`inbox.folder_missing`,
`preview.no_image`, `vision.model_busy`, `finding.secret`), имена параметров латиницей. Сообщение собирается функцией `messages.make(код, **параметры)` и ведёт себя как
прежняя строка: сравнение, поиск подстроки и печать дают русский текст. Кроме текста оно несёт `code` и `args`, а в JSON уходит как `{"code", "args", "text"}`. Неизвестный
код, лишний или недостающий параметр, значение не из строки, числа, булева и null — ошибка сборки: её ловят тесты, а не владелец. Системные слова (вид программы, вид
внедрения указаний, вид секрета) в параметрах не живут: параметр хранит код вида, русское слово берётся из таблицы `WORDS`, а английское подставляет плагин.

**Где применяется.** Отказы команд (`InboxError`, `ReviewError`, `IntakeError`, `KnownError`, `BatchError`, `PreviewError` и прочие) наследуют от `CodedError`. Команда с
`--json` при отказе пишет последней строкой stderr `{"error": {"code", "args", "text"}}` и возвращает 1; без `--json` — «ошибка: текст». Код возврата 2 — разбор аргументов,
у него объекта-сообщения нет. Замечания прохода — сообщения из каталога, в `квитанции/<пачка>.meta.json` у каждого есть код. У находок приёмки есть `msg` (что нашлось) и
`where_msg` (где), у записей квитанции — `reason_msg` и `notes_msg`; находка модели — единственный код без области, `llm_finding`. Поля `rule`, `level`, `where`, `quote`,
`reason` не изменили ни смысла, ни текста. Когда `quote` — цитата документа, в `args` стоит `quoted: true`: плагин показывает цитату только тогда.

**Английский словарь.** `dsh-plugin/lib/client.messages.js`: английский шаблон на каждый код, с теми же именами параметров, и английские слова видов. В шаблоне `{имя}` —
параметр, `{?…?}` — необязательная часть, которая показывается, только когда все её параметры не пусты. Имя файла, цитата документа и слова модели подставляются как есть.
Плагину пришёл неизвестный код — он показывает `text`, русский текст сервера: экран работает, только не по-английски.

**Сверка.** Словарь и каталог не должны разойтись, и это держат тесты. `dsh-plugin/test/client-messages.test.mjs` запускает `python3 tools/messages.py --json`, `--words` и
`--rules` и сравнивает коды, имена параметров, слова видов и перечень правил со словарём; расхождение называет код. `tests/test_messages.py` проверяет каталог с другой
стороны: каждое обращение к коду в `tools/` называет существующий код, а каждый код каталога кем-то используется; русские тексты кодов сверены с образцами «как было до
каталога».

## Индекс и поиск

LanceDB, таблица `docs` в `<каталог архива>/index/lance`. Её заводит `flyarchive init` (схема — `tools/ingest.py`), строки пишут приёмка (`ingest.index_documents`) и
дозаполнитель.

| Колонка | Что |
|---|---|
| `path` | путь относительно корпуса, ключ для чтения документа |
| `source` | база: для принятого через входящую папку — `входящие`; остальные имена задаёт таблица источников |
| `space` | раздел базы: каталог первого уровня, ящик или номер пачки |
| `title` | заголовок: тема письма, имя файла, ключ задачи |
| `updated` | дата документа, `ГГГГ-ММ-ДД` |
| `url` | ссылка на оригинал, если была |
| `chunk` | номер фрагмента внутри документа |
| `text` | сам текст фрагмента, до 4000 знаков |
| `vector` | вектор модели `embed_model` (по умолчанию `bge-m3`), размерность `embed_dim` (по умолчанию 1024) |

Индексов два: полнотекстовый по `text` (его заводит `init`) и векторный IVF-PQ. На свежей таблице векторного индекса нет: поиск по векторам идёт перебором, и на малом архиве
это незаметно; так же ищутся строки, добавленные после построения индексов. Векторный индекс строит `flyarchive index optimize` (`tools/index_optimize.py`: IVF-PQ с косинусным
расстоянием, на таблице от 20 000 строк, на процессоре; с ключом `--compact` ещё и уплотняет таблицу), а при переписывании таблицы с настоящими датами —
`flyarchive index dates --apply` (от 10 000 строк). Рядом лежит база известного `index/known.sqlite`: sha256 каждого файла корпуса, `Message-ID`, отпечаток и дата
каждого письма; по ней приёмка узнаёт то, что уже лежит в архиве.

### Как считается выдача

1. Два списка кандидатов: смысловой по векторам и точный по BM25 (полнотекстовый).
2. Объединение обратным рангом: `1.0/(60+ранг)` для векторов, `0.8/(60+ранг)` для BM25.
3. Умножение на свежесть: `0.55 + 0.45 × затухание`, период полураспада — настройка `search_half_life_days` (по умолчанию 540 дней); у документа без даты возраст считается
   десятилетним.
4. Схлопывание повторов по первым 400 символам текста.

Векторный поиск по индексу просматривает `search_nprobes` разделов (по умолчанию 400) и уточняет `search_refine` (по умолчанию 30) раз больше кандидатов по исходным
векторам: больше разделов — точнее и медленнее, и умолчания подобраны замером на большом индексе, где малые значения теряли заметную долю настоящих ближайших. Вектор
запроса считается на процессоре, пока не включена настройка `embed_gpu`. Фильтры выдачи — `since` (год, месяц или день), `source` (одна база или несколько через запятую),
`space`. Размер ответа для модели ограничивают `api_snippet_chars`, `api_max_k` и `api_budget_chars`. Тот же поиск доступен из терминала как `flyarchive search`
(и `python3 tools/search.py`), на странице поиска и по `/api/search`: общий код — `tools/search.py`.

Дата документа — настоящая: у письма из заголовка, у вложения — дата его письма, задачи или страницы; у принятого через входящую папку — по порядку: свойства файла, дата в
имени, время изменения, день приёмки.

## Каталог архива

Каталог архива — `~/flyarchive` или `FLYARCHIVE_HOME`; кода в нём нет, только запускалка команды `bin/flyarchive`. Имена рабочих каталогов (`входящие`, `очередь`, `карантин`, `квитанции`, `удалённое`) русские.

```
<каталог архива>/
  corpus/
    входящие/<пачка>/   принятое через входящую папку и по MCP
    <корень>/           выложенные вручную выгрузки; имена корней — в таблице источников
    _карантин/          каталоги с таким именем в корпусе обход пропускает: в индекс они не идут
  index/                lance/ — индекс, known.sqlite — база известного, pending.jsonl — долги индексации,
                        vision-pending.jsonl — долги описания, vision/<sha256>.json — описания изображений,
                        ingested.txt — пройденные дозаполнителем файлы
  входящие/             входящая папка по умолчанию (настроенная лежит вне архива)
  входящие-возврат/     папка возврата рядом со входящей: то, что архив не взял
  очередь/<пачка>/      документы с находками, ждут решения
  карантин/<пачка>/     программы и негодные архивы
  квитанции/            <пачка>.jsonl — записи приёмки и решения владельца, <пачка>.meta.json — длительность и замечания
  удалённое/<день>/     убранные из архива документы
  cache/preview/        кэш просмотра: производный, чистится по возрасту и объёму
  settings.json         настройки (необязательный файл)
  sources.json          таблица источников (необязательный файл)
  inbox.json            настройка приёмки
  preview.json          образ контейнера просмотра: имя и дайджест
  protected-paths       каталоги, которые не отдаются песочнице (необязательный файл)
  dsh.patch.yml         файл настройки оболочки: пишет установка
  bin/flyarchive        запускалка команды (sh): пишет установка, ссылка в каталоге команд ведёт на неё
  inbox-state.json      что видел прошлый проход во входящей папке: по нему файл, переставший меняться, считается готовым к разбору
  inbox-progress.json   ход разбора: есть, только пока идёт проход
  secrets/              хеши токенов, ключ подписи ссылок, служебный токен
  logs/                 журнал обращений и логи служб
```

Каталог закрыт от других пользователей машины: 700 на каталогах, 600 на файлах (`flyarchive perms check`).

## Требования и проверенная конфигурация

Нужны: Linux (Ubuntu 24.04, в том числе в WSL2; другие системы код не запускает), Python 3.10 или новее, библиотеки `lancedb`, `pyarrow` и `pymupdf`, служба векторов
с интерфейсом `/api/embed` и моделью `bge-m3`. Остальное необязательно: bubblewrap, `7z`, graphviz, docker, systemd, `dsh` с node, tailscale, локальная модель с интерфейсом
OpenAI. Что без чего работает — в `docs/operations.md`, раздел «Что нужно и проверка окружения»; проверить окружение можно командой `flyarchive doctor`.

Проверено на: Ubuntu 24.04, Python 3.12, `lancedb` 0.38, `pyarrow` 25, `pymupdf` 1.28 (нижние границы в `requirements.txt` совпадают с этими версиями), node 22 для плагина,
плагин собран под `@deepseek-ai/cordis` `~4.0.4`. Чем проверено: набором тестов на подставных службах (векторы, локальная модель, `systemctl`, docker) и сквозным набором
`dsh-plugin/e2e/run.sh` с настоящими DSH и Chromium; запуск тестов описан в `docs/operations.md`. Набор тестов Python прогнан и на `lancedb` 0.40 — последней на день выпуска. Чего набор не доказывает: работу с версиями библиотек выше названных, с
другими серверами локальной модели (их заменяет подставной сервер с интерфейсом OpenAI, `tests/test_local_server.py`) и на других дистрибутивах — это стоит проверить на своей
установке (`flyarchive doctor`, затем `flyarchive init` и один документ через входящую папку).
